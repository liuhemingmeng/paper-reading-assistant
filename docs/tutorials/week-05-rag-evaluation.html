PAPER READING ASSISTANT · WEEK 05

不只“能回答”，还要知道检索是否正确

1. 为什么要评测

RAG 输出有两层不确定性：检索是否拿到了真正相关的证据，以及模型是否忠实使用了这些证据。第 4 周已经实现“检索证据 → 只传证据给模型 → 原样返回 citations”。第 5 周先解决第一层：同一批问题在一次改动前后，检索是否更容易找到正确页。

本周已完成

新增可调用的 retrieval evaluation API、Pydantic 评测样本模型、逐题命中明细、Recall@K、MRR，以及覆盖全命中、第二名命中、未命中、未建索引和非法样本的回归测试。

本周边界

本周不把模型生成的语言质量折算成一个“万能分数”。答案忠实度、覆盖度和表达质量需要人工标注或专门裁判模型，留给下一阶段扩展。

2. 评测集：问题必须有可核验目标

一个样本由自然语言问题和目标证据页码组成：

{
  "question": "What measures ranking quality?",
  "expected_page_numbers": [2]
}

页码是当前最合适的标注单位：第 3 周 PDF 处理管道已经稳定保存它；你可以打开原 PDF 人工核验；而数据库里的 chunk id 会在文档重传后变化。一个问题允许多个目标页，因为跨页论证或多个可接受证据都很常见。

样本质量原则说明
问题具体“方法检索什么？”优于“这篇论文讲什么？”
目标可定位标注能直接支持答案的页，而不是仅提到相关主题的页
覆盖不同难度事实型、定义型、方法型、比较型问题都要有
标注可复查保留对 PDF 原页的人工核验记录

3. 两个核心指标：Recall@K 与 MRR

设问题 i 的目标页码集合为 Rᵢ，前 K 个检索结果页码序列为 Lᵢ。

3.1 Recall@K：前 K 个里是否找到至少一个证据

Hit@K(i) = 1, if any(page in Rᵢ for page in Lᵢ)
Recall@K = mean(Hit@K(i))

例：10 个问题中，前 3 个结果找到了目标页的有 8 个，则 Recall@3 = 0.8。它回答“系统是否把证据找回来了”。当前每个问题都至少有一个正确页，所以这里称为问题级 evidence recall。

3.2 MRR：第一个正确证据排得多靠前

RR(i) = 1 / first_relevant_rank
MRR = mean(RR(i))
第一个目标证据位置RR解释
第 1 名1.0最佳：用户或生成器马上看到关键证据
第 2 名0.5命中但排序仍有改进空间
第 3 名0.333Top-K 足够大时仍可用，但噪声更大
未命中0检索没有找到目标证据

Recall@K 和 MRR 需要一起看：一个系统可能 Recall@3 很高，但正确证据总排第 3；也可能第 1 名常常正确，但少量困难问题完全丢失。

4. 评测代码流程

1. 输入 cases：API 接收 EvaluationCaseRequest，Pydantic 拒绝空问题、空目标页、非正页码。
2. 检索：每道题复用第 4 周同一个 retrieve_chunks()，因此评测的是生产路径而不是另一套“测试检索器”。
3. 找首个相关结果：依次遍历检索页码，第一项命中目标页时记录 rank。
4. 汇总：按题均值计算 Recall@K 与 MRR。
5. 返回明细：每个样本返回 expected pages、retrieved pages、hit、reciprocal rank，使均分可审计。
report = evaluate_retrieval(
    cases,
    lambda question, k: retrieve_page_numbers(question, k),
    k=3,
)

注意：搜索接口对“无词面相关证据”的普通用户查询返回 422；而评测会把这种场景转为一个空检索列表，记录为 miss。否则一个失败样本会中断整个评测，反而掩盖系统薄弱点。

6. 引用一致性不是“显示几个页码”

第 4 周问答服务先调用 retrieve_chunks()，随后用返回的同一列表做两件事：格式化 LLM evidence prompt；构造 API 响应的 citations。这保证 citations 不是事后重新搜索得到的另一批片段。

当前可保证什么

答案接口返回的 citations 与模型实际见到的 evidence 来自同一个业务对象列表。当前检索评测则验证该列表中是否含有人类标注的目标页。

当前还不能保证什么

即使 citation 正确，LLM 仍可能误读、过度概括或遗漏证据。下一阶段要增加 answer faithfulness 的人工标注或裁判模型评测。

人工验收时不只看总分：检查每道题的 retrieved pages 是否合理，特别记录未命中题和“命中但排得很靠后”的题。这些失败案例会指导你后续改进 chunk、embedding 或 query 处理。

9. 常见误区

不要拿 2 道题的 100% 当成模型结论

小样本只证明链路可运行。要比较 embedding 方案，至少需要覆盖不同章节、问法和难度的固定问题集，并将新旧方案跑在同一集合上。

不要把 page hit 等同于 answer correct

页码命中只是 retrieval 的代理指标。一页可能有多个段落，模型也可能错误推理；因此不能把 Recall@K 直接宣传为问答准确率。

不要边改索引边改评测集

想比较版本时，问题、目标页、K 值必须固定。否则分数变化无法归因于系统改进还是测试标准变化。

10. 建议独立练习

  • 为一篇公开论文创建 10 条问题和目标页标注，并解释每题为什么选择这些页。
  • 用同一评测集比较 K=1、3、5 的 Recall 与 MRR，分析为什么 K 变大通常提高 recall 却可能增加生成噪声。
  • 给评测结果增加“目标页最小排名”字段，并写回归测试。
  • 将样本导出为一个被 Git 跟踪的脱敏 JSON fixture，思考 schema 演进和版本号。
  • 设计一个 citation correctness 人工打分表，区分引用是否存在、是否相关、是否充分支持答案。

11. 第 6 周：真实 embedding 对照

第 6 周不应直接“换一个更强模型”就宣布提升。应实现一个符合 TextEmbedder 协议的真实 embedding 客户端，将本周固定评测集同时跑在 hashing baseline 与真实 embedding 上，再按 Recall@K、MRR、失败案例和成本做取舍。
