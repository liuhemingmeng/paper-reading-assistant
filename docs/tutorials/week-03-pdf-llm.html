PAPER READING ASSISTANT · WEEK 03

从 PDF 文件到可追溯的阅读洞见

本周不只是“上传文件并调用模型”。目标是建立一条可测试、可解释、可扩展的数据管道：安全保存 PDF，逐页提取文本，保留来源，将外部 LLM 隔离在明确的客户端边界外。

1. 本周目标与边界

第 2 周只能管理论文元数据。第 3 周让系统真正理解一份文本型 PDF：文件被保存、页级文本被提取、文本按块持久化，并可在配置 OpenAI 兼容模型后生成摘要和阅读问题。

本周已完成

实现 PDF 上传、10 MiB 限制、UUID 存储名、PyMuPDF 文本提取、页码/章节分块、文档与分块持久化、重新上传替换、论文删除清理文件、结构化 LLM 客户端、重试与 24 个测试。

刻意不做

扫描型 PDF 的 OCR、向量数据库、检索增强生成、异步任务队列和多文档知识库都不在本周范围。先把输入文本与来源信息做可靠，后续 RAG 才有可信基础。

2. 全链路数据流

1. 创建 Paper：先获得稳定的 paper_id，它是整个文档生命周期的根。
2. 上传 PDF：UploadFile 按 1 MiB 块写到 data/uploads/paper-{id}/UUID.pdf。
3. 解析：PyMuPDF 逐页读取文本，空文本或损坏文件立即失败。
4. 分块：段落优先，长文本按上限切分；每块保留页码、章节标题和序号。
5. 落库：写入 PaperDocument、PaperChunk，并更新 Paper 的文件路径。
6. 生成洞见：LLM 客户端读取完整文本，校验结构化 JSON，服务层写入 PaperInsight。

这里最重要的设计不是某个库，而是每一步都有清晰的输入、输出和失败处理。PDF 解析失败不能留下脏文件；LLM 配置缺失不能伪装成成功；重新上传不能混入旧分块。

3. 数据模型：为什么要保存来源

表核心字段解决的问题
Papertitle、authors、abstract、file_path论文的稳定业务实体
PaperDocumentpaper_id、原文件名、存储路径、页数、完整文本当前已处理 PDF 的元数据与原始提取结果
PaperChunksequence、page_number、section_title、content后续检索时的最小证据单元
PaperInsightsummary、questions_json、model、status一次模型生成结果的可查询记录
Paper 1 ─── 1 PaperDocument 1 ─── N PaperChunk
   │
   └────────────────────────────── N PaperInsight

RAG 的回答必须能说明“依据来自哪里”。仅保存一串切分后的文本，无法在回答后定位原始页码；保存 page_number 和 section_title 后，检索结果可以被转换成“第 7 页 Method”这样的证据引用。

重新上传的契约

一篇 Paper 当前只对应一个 PaperDocument。上传新文件时，旧文档记录及其 chunks 通过 ORM 级联删除，旧 PDF 也会被删除。这是“替换”而不是“追加”，避免旧版本文本污染检索。

4. 安全上传：文件不能直接相信

浏览器传来的文件名和 MIME 类型都是客户端声称的信息，不应被直接用于本地路径。实现采用三个最小但关键的限制：

  • 仅接受文件名以 .pdf 结尾的上传。
  • 仅接受 application/pdf、通用二进制 MIME，或缺失的 MIME；最终仍由 PyMuPDF 解析验证内容。
  • 用随机 UUID 作为磁盘文件名，原文件名只保存为元数据。
async def save_upload(upload: UploadFile, paper_id: int, root: Path) -> tuple[Path, int]:
    validate_pdf_upload(upload)
    target_path = root / f"paper-{paper_id}" / f"{uuid4().hex}.pdf"
    with target_path.open("wb") as destination:
        while content := await upload.read(1024 * 1024):
            size += len(content)
            if size > MAX_UPLOAD_BYTES:
                raise PDFProcessingError("PDF exceeds the 10 MiB upload limit")
            destination.write(content)

分块写盘的意思是控制峰值内存。这里 10 MiB 并不巨大，但这个模式会在以后处理更大文件、对象存储和流式处理时继续成立。任何异常都会执行 unlink(missing_ok=True) 清理不完整文件。

5. 文本提取与分块：为检索做准备

5.1 页级提取

with pymupdf.open(path) as document:
    pages = [
        ExtractedPage(page_number=index, text=normalize_text(page.get_text("text")))
        for index, page in enumerate(document, start=1)
    ]

page.get_text("text") 只读取 PDF 已有的文本层。扫描件看起来像有文字，但其实只包含图片，因此会得到空字符串。系统对此返回 422 并明确说明 OCR 尚未支持，而不是生成空摘要。

5.2 分块策略

分块不是机械把全文每 1200 个字符切一刀。实现先将规范化文本按行视作段落；识别如 1 Introduction 的短标题后，更新当前章节上下文；普通段落在不超过 1200 字符时原样保存，超长段落优先向句号或换行回退，并保持 160 字符重叠。

规则原因
段落优先比固定长度切分更少破坏语义
1200 字符上限控制后续 embedding 和 LLM 上下文成本
160 字符重叠降低边界处论证被截断的概率
页码与章节标题让每个检索结果具备来源
这是启发式，不是通用论文结构解析器

多栏 PDF、断词、表格、公式、中文标题样式都会降低规则效果。本周的正确目标是得到稳定、可检验的基础文本块；后续若真实样本暴露问题，再引入更专门的版面分析或标题识别策略。

6. API 路由与服务层：边界要分开

接口成功职责
POST /papers/{id}/document201上传、保存、解析、分块、持久化
GET /papers/{id}/document200返回当前文档元数据
GET /papers/{id}/chunks200按顺序分页查询可追溯文本块
POST /papers/{id}/insights:generate201生成并落库摘要与问题
GET /papers/{id}/insight200读取最近一次洞见

api.py 处理 HTTP：接收 multipart、选择状态码、把领域异常转换为 404/422/503/502。services.py 处理业务事务：替换旧文档、创建 chunks、生成并保存 insight。PDF 模块不依赖数据库，LLM 客户端不依赖 FastAPI。这样每层都能独立测试和替换。

7. LLM 客户端：把不可靠的网络放在边界

LLM 是外部服务，可能缺配置、限流、超时、返回非 JSON 或变更格式。因此不应在路由函数里直接写 HTTP 请求。OpenAICompatibleClient 将这类不确定性集中处理。

payload = {
    "model": self.model,
    "temperature": 0.2,
    "response_format": {"type": "json_object"},
    "messages": [...],
}
response = client.post(f"{self.base_url}/chat/completions", headers=headers, json=payload)
机制目的
本地 .env + 环境变量配置与代码分离，且系统环境变量优先
30 秒总超时避免请求无限占住工作线程
最多 3 次指数退避仅针对超时、网络错误、429、5xx 等短暂故障
response_format 与二次解析即使模型承诺 JSON，也在代码中验证契约
恰好 5 个非空问题将提示要求转为可检验的程序约束

这里的 InsightGenerator 协议让服务层只依赖 generate(text)。测试可传入 FakeGenerator，生产才使用 HTTP 客户端。这种依赖倒置是可测试 Agent/RAG 系统的基础手法。

8. 错误语义：失败必须可判断

情况状态码含义
Paper、文档或洞见不存在404请求的资源不存在
非 PDF、过大、损坏、无文本 PDF422请求已到达服务，但内容不可处理
缺少 LLM 配置503当前服务无法提供模型能力
LLM 最终失败或返回非法结果502上游模型服务或其响应不符合契约

状态码不是装饰。调用方可以根据它决定是否提醒用户上传可搜索 PDF、是否提示配置环境变量、是否稍后重试。把所有错误都变成 500 会把可恢复问题伪装成系统故障。

9. 自动化测试与手工验收

测试不提交 PDF 附件，而是使用 PyMuPDF 在运行时生成最小 PDF。这使仓库保持轻量，也避免测试依赖版权文件或不可控二进制样本。

  • 上传成功：页数、存储路径、页码和章节来源都正确。
  • 重新上传与删除：旧文件被删除，旧块不再存在，删除 Paper 时关联文件也会清理。
  • 失败输入：非 PDF、空文本 PDF、未知 Paper 返回稳定错误。
  • Fake LLM：验证洞见写库，不请求真实网络也不需要密钥。
  • 缺配置：洞见路由返回 503，证明不会意外访问外部服务。

11. 常见坑与本周决策

不要把 API Key 写进代码、README 或测试

密钥应只存在于本机环境变量或被忽略的 `.env`。一旦提交到 Git，即使后续删除，历史记录中仍可能保留它；应立即吊销并更换。

不要把 SQLite 主键变化当成替换语义

SQLite 删除后可能复用整数主键。因此重新上传测试验证的是新文件名、旧文件消失和 chunks 内容被替换，而不是 document id 必然变化。这是区分“实现偶然现象”和“业务契约”的典型例子。

不要把完整 PDF 文本直接塞进每次模型提示

当前仅为单文档基础能力截取最多 40,000 字符。第 4 周应先检索最相关 chunks 再交给模型，降低成本与上下文噪声，并把来源随答案返回。

12. 建议独立完成的练习

  • 为 GET /papers/{id}/chunks 增加 page_number 可选过滤，并补充 404、空列表与分页测试。
  • 在 PDF 元数据中增加 SHA-256 文件哈希，用于识别同一 Paper 的重复上传；先写测试，再决定重复文件是拒绝还是复用。
  • 为 OpenAICompatibleClient._parse_response() 补充单元测试：缺少 choices、questions 不是列表、问题数量不为 5、空字符串等。
  • 让 PaperInsight 保存生成时的文本长度和模型耗时，但不要记录 API Key 或完整请求头。
  • 寻找一篇公开的双栏 PDF，记录标题识别、公式、表格和断词表现，提出一个最小改进并附回归测试。

13. 第 4 周：向量检索与 RAG

第 3 周已经产出 RAG 的关键原料：每个 PaperChunk 都有文本、顺序、页码与章节。第 4 周应将 chunk 变成向量，按用户问题检索 Top-K 证据，再把“问题 + 证据块 + 引用信息”交给模型生成回答。

第 4 周的验收标准

系统不只回答，还应返回命中的原文片段和页码；并用一组固定问题评估检索是否找对证据。没有来源的流畅回答不等于可靠的 RAG。
