检索命中 ≠ 答案正确：评测 RAG 的“回答质量”

1. 为什么还要评答案质量

第 5 周的 Recall@K / MRR 回答的是“证据找得对不对”。但即使证据找对了，生成阶段仍可能出错：

编造来源：答案写“见第 5 页”，但检索只返回了第 1、2 页——这是可追溯性的硬伤。
幻觉事实：答案包含证据里根本没有的信息，却看起来合理。
未归因：答案正确但没指出依据页，读者无法复核。

RAG 的“可信” = 检索质量 × 生成质量。只评一边都会高估系统。第 7 周把两维合并到同一份固定评测集上，让“找得对”和“用得对”一起被回归。

2. 端到端评测流水线

每条评测用例执行同一条真实请求链路，只是最后多两步评分：

检索：对问题做 Top-K 检索，得到证据块与页码（复用第 5 周 Recall@K/MRR）。
生成：用 answer_question 只把证据喂给生成器，得到答案与 citations（第 4 周契约）。
引用校验：从答案文本抽页码，比对证据页码集合。
忠实裁判（可选）：把 (问题, 证据, 答案) 交给 LLM 裁判，返回 faithful + 理由。
汇总：检索指标 + 引用正确率 + 忠实率，逐题明细 + 聚合。

全程不重写检索或问答逻辑，只在它们外围加“评分”层。这正是可维护评测系统的形状：被测对象是既有功能，评测是独立的、可替换的。

3. Citation Correctness：零成本的硬检查

很多 RAG 答案会在正文里写“见第 N 页”。如果 N 不在检索证据里，就是凭空引用。我们用正则从答案文本抽显式页码，支持英文与中文：

_CITED_PAGE_PATTERNS = [
    re.compile(r"page\s+(\d+)", re.IGNORECASE),
    re.compile(r"p\.?\s*(\d+)", re.IGNORECASE),
    re.compile(r"第\s*(\d+)\s*页"),
]

def check_citation_correctness(answer, evidence_pages):
    cited = extract_cited_pages(answer)
    unsupported = [p for p in cited if p not in evidence_pages]
    return CitationCheck(
        cited_pages=cited,
        evidence_pages=sorted(evidence_pages),
        unsupported_pages=unsupported,
        consistent=len(unsupported) == 0,
    )
为什么这是“硬检查”

它不需要任何模型、任何网络、任何密钥。只要答案敢写页码，我们就验证那个页码确实在系统给模型的证据里。遗漏（答案没写页码）不算违规，但会在报告里以 cited_pages == [] 暴露，提示“答案未显式归因”。

注意 extract_cited_pages 对相同页码去重——引用校验关心“引用了哪些页”，而不是“引用了几次”。

4. Faithfulness：LLM 作为裁判

引用正确只证明“页码没编造”，不证明“事实没编造”。忠实度要求裁判判断：答案的每一个事实声称是否都能在证据中找到依据。

我们定义 FaithfulnessJudge 协议，并给出 OpenAICompatibleFaithfulnessJudge，沿用第 3 周 LLM 客户端的边界纪律：

配置：from_environment() 读 LLM_* 三件套，缺任一抛 LLMNotConfiguredForJudgingError。
请求：要求模型返回 JSON {faithful: bool, reason: str}，temperature=0。
重试：429/5xx/超时/网络错误最多 3 次退避。
解析：缺 faithful 字段或无法解析 → 抛 FaithfulnessError。
class FaithfulnessJudge(Protocol):
    def judge(self, question, evidence, answer) -> FaithfulVerdict: ...

@dataclass(frozen=True)
class FaithfulVerdict:
    faithful: bool
    reason: str
裁判也有局限

LLM 裁判会误判，且本身消耗 token。它给出的是“可回归的软信号”，不是金标准。报告里 faithful_rate 与 faithfulness_reason 都应被人工抽查，而不是当最终真理。

5. 端到端报告：一次跑出两维指标

evaluate_answers 把检索评测和答案评测合在一起，输出一个报告：

字段含义
recall_at_k / mean_reciprocal_rank检索质量（第 5 周）
citation_correct_rate所有用例中“未编造页码”的比例
faithfulness_run本次是否跑了忠实度裁判
faithful_rate忠实比例；未跑裁判时为 null
results[]逐题：答案、引用页、证据页、引用一致、忠实、理由

关键设计：judge=None 时报告仍然完整——检索指标和引用正确率照常输出，只是 faithful_rate 为 null。这保证“没配 LLM 也能回归大部分质量”，而不是整条评测瘫痪。

6. API 与错误边界

新增路由复用第 4/5 周的错误处理风格：

POST /papers/{paper_id}/answers:evaluate
  body: [{ "question": "...", "expected_page_numbers": [1], "expected_answer_pages": [1] }]
  query: k=3, run_faithfulness=false
条件状态码来源
未配置 LLM（生成答案）503LLMConfigurationError
run_faithfulness=true 但未配置裁判503LLMNotConfiguredForJudgingError
未建索引409RetrievalNotReadyError
空问题 / 无关证据422校验或 NoRelevantEvidenceError
embedding / LLM 调用失败502对应 ResponseError

和第 3、6 周一致：未配置外部服务时返回 503，绝不把请求发到未知地址。

7. 命令行评测

scripts/evaluate_answers.py 让你对本地数据库跑完整评测，无需起服务：

# 离线演示：用假生成器，引用正确性链路可全程跑通（无需任何 LLM 凭据）
python scripts/evaluate_answers.py --paper-id 1 --cases cases.json --fake

# 真实运行（需要 .env 配置 LLM_*）
python scripts/evaluate_answers.py --paper-id 1 --cases cases.json --faithfulness

cases.json 是评测用例数组：

[
  {"question": "方法检索了什么证据？", "expected_page_numbers": [1], "expected_answer_pages": [1]},
  {"question": "实验报告了什么结果？", "expected_page_numbers": [2]}
]
为什么提供 --fake

你本地没有 LLM 凭据时，--fake 让生成器把证据页作为引用写进答案，从而真实演示“引用正确性检查”如何跑通与如何拦截编造页。这是把“评测系统”本身做成可运行、可演示的工件，而不只是测试里的内部函数。

9. 常见误区

不要只信忠实度分数

faithful_rate 来自另一个 LLM，它会误判、会奉承、会漏检。把它当可回归信号，配合 faithfulness_reason 人工抽查，而不是当最终结论。

引用正确 ≠ 事实正确

答案写“见第 1 页”且第 1 页确实在证据里，只能证明没编造页码；第 1 页里有没有支持该断言的内容，需要忠实度或人工判断。两维要一起看。

未配置也要能回归

评测系统最怕“没密钥就全挂”。第 7 周让引用正确性（占用最大头的可检查项）完全离线，只有忠实度是可选外挂，避免把质量回归锁死在外部服务上。
