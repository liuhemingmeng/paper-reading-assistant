第8周实验报告：本地哈希基线 vs 火山语义向量

论文阅读助手 · 检索质量量化对比实验 · 生成时间 2026-08-15
一句话结论：在 12 条受控问句上，火山 doubao-embedding-vision-251215 取得 Recall@K = 1.0、MRR = 1.0 的满分；本地哈希基线在 k≥3 也能 100% 召回， 但 k=1 的 MRR 只有 0.944（语义改写类问句仅 0.833）——它把含"training"一词的问句错排到了第 1 页。 这说明：Recall@K 看不出两种检索器的差距，MRR（排第一的质量）才能暴露。

1. 实验目的与方法

目标：把第 4–6 周做好的"可替换 Embedding"能力，从"代码能跑"推进到"生产可对比"——用同一组固定评测集， 量化本地哈希基线（LocalHashingEmbedder）与真实语义向量（火山方舟多模态 embedding）的检索质量差异。

  • 受控文档：6 页合成论文，每页一个独立主题（Background / Vector Index / Chunking / Evaluation / Fine-tuning / Deployment），共切出 12 个 chunk。
  • 评测集：12 条问句，分两类—— 字面类（lexical）直接复用原文词汇（两类检索器都应命中）； 语义类（semantic）用原文没有的同义词改写（只有语义模型应能稳定定位）。
  • 指标：Recall@K（前 K 个结果是否含正确页）与 MRR（正确页排第几的倒数，越接近 1 越好），K = 1 / 3 / 5。
  • 流程：对每个检索器，分别建索引 → 对同一回调跑评测，全程走与线上一致的 build_retrieval_index / retrieve_chunks / evaluate_retrieval 链路。

基线的典型失误（可写进简历的案例分析）：第 5 页讲"对比学习（contrastive loss）把匹配句对拉近"， 但问句用的是 "embedding training / matching pairs" 这类词。本地哈希基线因为 "training" 也出现在第 1 页 （"training data"），余弦相似度被表面词重叠带偏，把第 1 页排到了第一；语义向量理解句义，正确锁定第 5 页。 这正是词汇重叠陷阱，也是语义 embedding 的核心价值。

4. 结论与简历要点

  • 语义 embedding 在"排第一"上更可靠：火山模型 MRR = 1.0，意味着生成的答案永远以最相关页为证据；本地基线偶发误排（MRR 0.944）。
  • Recall@K 会掩盖问题：两者在 k≥3 都 100% 召回，单看 Recall 会误以为"基线够用"；只有 MRR 暴露了 top-1 质量差距。这是评测指标选型的重要教训。
  • 语义改写类问句是分水岭：基线在字面问句上满分，但在同义改写问句上 k=1 MRR 跌到 0.833——真实用户提问往往就是这样，所以生产环境必须用语义模型。
  • 可替换设计的价值：同一套 TextEmbedder 协议，离线用哈希基线保证测试确定性，线上切真实模型即获得质量提升，无需改任何检索/评测代码。

5. 如何复现

实验脚本 scripts/compare_embeddings.py 已提交，文档与评测集内联其中、完全可复现。

# 仅本地基线（无需任何密钥）
python scripts/compare_embeddings.py

# 接入火山真实模型（需 .env 配置 EMBEDDING_*，并绕过可能拦截外部域名的代理）
unset http_proxy https_proxy
python scripts/compare_embeddings.py --out data/embedding_comparison.json

注：运行真实模型会向火山方舟发起约 60 次 embedding 请求；data/embedding_comparison.json 已被 .gitignore 忽略，不会进仓库。

局限与下一步：本基准是主题区分清晰的 6 页合成文档，基线表现已相当好。在噪声更大、主题交叠的真实论文语料上， 语义模型的优势会进一步放大。下一步可：① 用真实论文 PDF（--pdf）复跑；② 配置真实 LLM_* 跑第 7 周的 answers:evaluate --faithfulness，把"检索质量"延伸到"答案质量"。
