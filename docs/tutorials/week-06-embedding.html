1. 为什么要可替换 embedding

第 4 周为了“不依赖大模型就能跑通 RAG”，用了一个本地 hashing 向量作为基线：把文本切成 token，用 token 哈希把词面散列到固定维度向量，再归一化做余弦相似度。它零依赖、可复现，但本质是词面匹配——换种说法、同义词、跨语言就找不到。

真实 embedding 模型把语义编码进向量，能跨越这些表述差异。但“真实”也意味着：需要网络、需要密钥、需要成本、需要选模型。把两者都做成同一协议的不同实现，就能在“可离线、可测试”和“更接近生产”之间切换，而不重写检索链路。

2. TextEmbedder 协议：唯一的契约

业务层只认这一个方法。只要对象有 embed(text) -> EmbeddedText，它就是可用的嵌入器：

class TextEmbedder(Protocol):
    def embed(self, text: str) -> EmbeddedText:
        """Turn text into a vector suitable for cosine similarity search."""

@dataclass(frozen=True)
class EmbeddedText:
    vector: list[float]
    model: str

注意 EmbeddedText 不只返回向量，还返回 model 名字。这个名字会写进 ChunkEmbedding.model，它是后面“同源校验”的关键。真实客户端把模型名设成你配置的 EMBEDDING_MODEL；本地基线固定为 local-hashing-v1。

3. 真实客户端：复用 OpenAI /embeddings 契约

OpenAI 兼容 embedding 接口是 POST {base_url}/embeddings，请求体 {"model": ..., "input": [text]}，返回 {"data": [{"embedding": [...]}]}。我们的客户端与第 3 周 LLM 客户端保持同样的边界纪律：

配置来源：from_environment() 读 EMBEDDING_* 三件套，缺任一即抛 EmbeddingConfigurationError。
重试：429/5xx/超时/网络错误最多 3 次指数退避。
归一化：返回向量立即 normalize()，使余弦相似度等于点积，和本地基线一致。
校验：响应不是对象、data 为空、embedding 不是数字列表，都抛 EmbeddingResponseError。
def embed(self, text: str) -> EmbeddedText:
    payload = {"model": self.model, "input": [text]}
    headers = {"Authorization": f"Bearer {self.api_key}", "Content-Type": "application/json"}
    for attempt in range(3):
        try:
            with httpx.Client(timeout=self.timeout) as client:
                response = client.post(f"{self.base_url}/embeddings", json=payload, headers=headers)
            if response.status_code == 429 or response.status_code >= 500:
                raise httpx.HTTPStatusError(...)
            response.raise_for_status()
            return self._parse_response(response.json())
        except (httpx.TimeoutException, httpx.NetworkError, httpx.HTTPStatusError) as error:
            last_error = error
            if attempt == 2:
                break
            time.sleep(0.5 * (2**attempt))
为什么归一化很重要

本地基线存的是单位向量，真实模型未必返回单位向量。若不归一化，余弦相似度就不能简化为点积，且不同模型维度不同会导致比较尺度混乱。在边界层统一归一化，业务层就只用关心“分数越高越相关”。

4. 配置驱动的选择：一套代码，两种运行

get_default_embedder() 在应用启动时决定用哪个嵌入器：

def get_default_embedder() -> TextEmbedder:
    load_local_env()
    base_url = os.getenv("EMBEDDING_BASE_URL", "").strip()
    api_key = os.getenv("EMBEDDING_API_KEY", "").strip()
    model = os.getenv("EMBEDDING_MODEL", "").strip()
    if all((base_url, api_key, model)):
        return OpenAICompatibleEmbedder(base_url=base_url, api_key=api_key, model=model)
    return LocalHashingEmbedder()

测试也可以显式注入：create_app(embedder=MyFakeEmbedder())。这使得“换嵌入器”成为启动参数，而非散落在各路由的 if/else。

环境变量作用缺省
EMBEDDING_BASE_URL兼容 OpenAI 的 embeddings 端点前缀三者缺任一 → 本地 hashing 基线
EMBEDDING_API_KEYBearer Token
EMBEDDING_MODEL模型名，同时作为向量来源标识

5. 索引与查询必须同源

余弦相似度要求两个向量来自同一个映射。若索引用“真实模型 1536 维”，查询用“本地基线 256 维”，维度都不一致，算出来的分数毫无意义。

因此 create_app 启动时只确定一次 app.state.embedder，索引路由和检索路由都用它。更进一步，retrieve_chunks 在查询时校验：

stored_models = {embedding.model for _, embedding in records}
if query_embedded.model not in stored_models:
    raise RetrievalNotReadyError(
        f"Paper {paper_id} index was built with {sorted(stored_models)} "
        f"but the query uses {query_embedded.model}; rebuild the index"
    )
防御的是哪类事故

你昨天用本地基线建了索引，今天配了真实 embedding 但忘了重建。查询会立刻收到 409 并要求重建索引，而不是默默返回一个看似合理的错误答案。

6. API 与错误边界

路由契约没有变化，只有内部错误映射增加了 embedding 相关项：

错误条件状态码来源
真实 embedding 超时/网络/429/5xx 用尽502EmbeddingResponseError
查询嵌入器与已建索引模型不一致409RetrievalNotReadyError
未建索引409原有逻辑
未配置 embedding 但强行调用外部（不会发生）—因为 get_default_embedder 已回退基线

关键区别：LLM 未配置时回答接口返回 503（避免误请求未知服务）；而 embedding 未配置时系统不会报错，只是静默使用本地基线——因为基线本身就是合法的、可运行的嵌入器。

7. 用同一评测集对比两种模型

第 5 周的价值在这里显现：固定问题集不随模型变化。流程是：

1. 基线记录：不配置 embedding，建索引，跑 retrieval:evaluate，记下 Recall@K 与 MRR。
2. 切换模型：填好 .env 的 EMBEDDING_*，重启服务。
3. 重建索引：对同一论文再调一次 retrieval:index（旧向量会被覆盖）。
4. 重跑评测：同一问题集、同一 K，读新指标与每题明细。
5. 归因：找出“基线 miss、真实模型 hit”和“反过来退化”的题，它们是选型的依据。
# 基线
curl -X POST http://127.0.0.1:8000/papers/1/retrieval:index
curl -X POST "http://127.0.0.1:8000/papers/1/retrieval:evaluate?k=3" -d @eval-set.json

# 配置真实 embedding 并重启后
curl -X POST http://127.0.0.1:8000/papers/1/retrieval:index
curl -X POST "http://127.0.0.1:8000/papers/1/retrieval:evaluate?k=3" -d @eval-set.json
切换后必须重建索引

第 6 周不会自动删除旧向量。因为模型变了，旧向量与新查询不可比；务必重新 retrieval:index。若忘记，查询会命中第 5 节说的 409 防护。

10. 常见误区

不要把“换了更强模型”当结论

只有在同一固定评测集上、且旧索引已重建、K 不变时，指标提升才可归因于模型。否则分数差异可能来自测试标准漂移或索引残留。

不要让检索和生成用两套 embedding

索引嵌入器和查询嵌入器必须是同一个。若将来分别配置，检索分数会失真。当前设计把两者绑定在 app.state.embedder，从结构上避免这个坑。

不要忽略维度与归一化

真实模型维度可能 768/1024/1536/3072 不等。向量存进 ChunkEmbedding.dimensions，但相似度能否成立仍取决于同源与归一化，这两个才是业务正确性，维度只是结果。

11. 建议独立练习

  • 不配置 embedding，跑第 5 周评测集，记录本地基线在几个同义问法上的 miss 案例。
  • 配置一个真实 embedding 端点（或本地镜像），重建索引后重跑同一集合，列出“基线 miss、真实 hit”的题。
  • 阅读 retrieval.py 的 LocalHashingEmbedder，解释为什么它无法处理同义词，并设计一句反问证明你的理解。
  • 为 get_default_embedder 增加一个“仅部分环境变量已设置”的断言测试，验证它不会半吊子启用真实模型。
  • 思考若未来要支持“每篇论文用不同 embedding 模型”，数据库和 API 需要改哪里、不必改哪里。

12. 第 7 周衔接
