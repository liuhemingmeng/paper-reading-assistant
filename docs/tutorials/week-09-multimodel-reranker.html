第9周教程：多模型注册表与 reranker 客户端

第 8 周我们接入了「一个」真实 embedding 模型，并建成了 138 篇真实评测语料库。但要回答「哪个 embedding / reranker 组合在我的语料上最好」这种能写进简历的问题，光有一个模型不够——我们需要一个可插拔的多模型底座，把候选模型登记好、能一键冒烟、能直接喂给后续语料级基准。本周落实三件事：Reranker 协议与硅基流动客户端、model_registry.py 模型登记、scripts/smoke_models.py 联网冒烟。

1. 为什么要两阶段检索（embedding + reranker）

单靠 embedding 向量做 Top-K 召回有两个固有弱点：

  • 向量维度有限：一个 1024 维向量要压缩整段语义，细粒度的「这个词是否真的相关」会被稀释。
  • 召回与精排混在一起：embedding 擅长「从全库里捞回可能相关的候选」，但不擅长「在 20 个候选里排出谁最相关」。

生产级 RAG 普遍用两阶段：

阶段干啥典型实现特点
召回 Recall从全库捞回 N 个候选（N 较大，如 20~50）Dense embedding / BM25便宜、高覆盖、精度一般
重排 Rerank对 N 个候选按相关性精排，取前 KCross-Encoder reranker贵、精度高、只看小集合

所以我们要让 reranker 与 embedder 一样「可插拔」——先有协议，后有具体厂商实现。这正是 Reranker 协议与 TextEmbedder 协议对称的原因。

2. Reranker 协议与硅基流动客户端

协议只定义一个方法，和 TextEmbedder.embed() 风格一致：

@runtime_checkable
class Reranker(Protocol):
    def rerank(self, query: str, documents: list[str], top_n: int | None = None) -> list[RerankHit]:
        """Reorder documents by relevance to query (most relevant first)."""

RerankHit 是一个不可变数据类，携带候选在原列表中的 index、相关性 score，以及可选的 document 文本。

硅基流动（SiliconFlow）的 rerank 接口是 OpenAI 兼容的 POST /v1/rerank：

payload = {
    "model": "Qwen/Qwen3-Reranker-4B",
    "query": "How does RAG reduce hallucination?",
    "documents": ["候选1", "候选2", "..."],
    "return_documents": False,
    "top_n": 5,            # 可选
}
# 返回 {"results": [{"index": 0, "relevance_score": 0.99}, ...]}
容错细节： 不同厂商字段名可能漂移——有的用 relevance_score，有的用 score。解析时两个都兼容；并对每个 hit 做边界校验（index 必须是 0~N-1 的整数、score 必须是数字），最后按分数降序排好再返回，调用方直接取下标 0 即最相关。

重试与错误边界和 embedding 客户端保持一致：429 / 5xx / 超时 / 网络错误做 3 次指数退避；解析失败抛 RerankResponseError。

3. 模型注册表：按短名实例化，密钥不进代码

后续语料基准要反复「用模型 A 建索引、用 reranker B 重排」。如果每处都手写 base_url + key + model，既冗长又容易把密钥提交进 Git。model_registry.py 把这件事集中起来：

# 只从 .env 读密钥，绝不硬编码
EMBEDDER_SPECS = [
    ("volcano-vision-251215",        ark_base,  EMBEDDING_API_KEY, "doubao-embedding-vision-251215",        "/embeddings/multimodal"),
    ("volcano-large-text-250515",    ark_base,  EMBEDDING_API_KEY, "doubao-embedding-large-text-250515",    "/embeddings"),
    ("siliconflow-qwen3vl-embed-8b", sf_base,   SILICONFLOW_API_KEY, "Qwen/Qwen3-VL-Embedding-8B",         "/embeddings"),
    ("siliconflow-qwen3-embed-0.6b", sf_base,   SILICONFLOW_API_KEY, "Qwen/Qwen3-Embedding-0.6B",          "/embeddings"),
    ("siliconflow-bge-m3",           sf_base,   SILICONFLOW_API_KEY, "BAAI/bge-m3",                         "/embeddings"),
]
RERANKER_SPECS = [
    ("siliconflow-qwen3vl-rerank-8b", "Qwen/Qwen3-VL-Reranker-8B"),
    ("siliconflow-qwen3-rerank-4b",   "Qwen/Qwen3-Reranker-4B"),
    ("siliconflow-qwen3-rerank-0.6b", "Qwen/Qwen3-Reranker-0.6B"),
]

密钥缺失的模型会被自动跳过（例如没填硅基 key 就不会出现硅基模型），所以离线子集也能跑。基准脚本只需：

from paper_api.model_registry import get_embedder_specs, get_reranker_specs, build_embedder, build_reranker

for spec in get_embedder_specs():
    embedder = build_embedder(spec)   # -> OpenAICompatibleEmbedder
for spec in get_reranker_specs():
    reranker = build_reranker(spec)   # -> SiliconFlowReranker

5. 一个真实踩坑：模型名对，但返回 404

现象： volcano-large-text-250515 报 Embedding request failed after 3 attempts，看不出原因。
排查： 直接 GET /api/v3/models 拉火山模型目录，发现该模型确实存在（名字一字不差），但状态是 Retiring（即将下线）；调用 embeddings 接口返回 404 InvalidEndpointOrModel.NotFound——意思是「对你这个密钥未开通 / 已下线」。
结论： 这不是代码 bug，是账号侧的模型可用性问题。可选动作：① 在火山控制台对该模型开通/创建推理端点；② 换一个状态为正常的 embedding 模型；③ 直接跳过它，用其余 8 个可达模型跑基准。

这个坑顺带暴露了客户端的一个缺陷：重试逻辑把底层错误吞成了「重试 3 次失败」，看不到真实原因。已修复——embedding 与 rerank 客户端在最终失败时，把 HTTP 状态码 + 厂商报错体 透出到异常信息里（见 _describe_http_error）。以后任何 4xx/5xx 都能直接定位，不用再写一次性诊断脚本。

7. 下一步：把 reranker 接进检索管线

客户端和注册表就绪后，真正的「生产级基准」还差两块：

  1. BM25 词法基线：行业金标准，用于和语义 embedding 对照（检验语义模型到底比词面匹配强多少）。
  2. reranker 接入 retrieve_chunks：先召回 N 个候选（embedding 余弦），再用 reranker 对这 N 个重排取 top-K。需要在服务层加一个可选的 reranker 参数。
  3. 语料级基准脚本：在 138 篇真实文档上，对 local-hashing / BM25 / 各 embedding × 是否接 reranker，跑 Recall@K、MRR、nDCG@K 并聚合到语料级指标。

届时「哪组配置最优」会由一个可复现的脚本给出，而不是凭感觉——这就是能写进简历的检索评测闭环。

给同学的一句话总结： 多模型比较的前提不是「多写几个 API 调用」，而是先把 协议 → 注册表 → 冒烟 这三层基础设施搭好；冒烟不是为了好看，而是为了在喂给重基准之前，就把「key 没填 / 模型下线 / 接口格式不符」这类环境问题一次性排干净。
