1. 目标与边界

“接入大模型问论文”不等于 RAG。真正的 RAG 要把问题转换成检索请求，找出可核验的原文证据，再约束生成阶段使用这些证据。第 3 周保存的 PaperChunk 已有页码、章节和顺序；第 4 周在此基础上补上向量、排序、引用和问答边界。

本周完成

新增 chunk embedding 持久化、确定性本地嵌入器、余弦相似度 Top-K 检索、索引/搜索/问答 API、证据 citations，以及 28 个回归测试。

刻意不做

本周不把 hashing vector 宣称为语义 embedding，也不引入云向量数据库。先把正确的数据流与可验证契约建立起来，下一阶段再比较真实 embedding 与索引方案。

2. RAG 的四个阶段

Embedding：把文本转换为固定长度向量，语义相近的文本理想情况下应更接近。
Indexing：为每个 chunk 保存向量、模型版本与维度，形成可查询的知识索引。
Retrieval：把用户问题向量化，与 chunk 向量比较，选出 Top-K evidence。
Generation：只把问题和 evidence 交给 LLM，再把 evidence 作为 citations 返回。

将这四步分开，才能定位失败究竟来自解析、embedding、检索还是模型回答。若答案不好，不能直接归因于“模型不够强”。

3. 为什么使用本地 hashing baseline

TextEmbedder 是一个协议，业务层只要求它能执行 embed(text)。默认实现 LocalHashingEmbedder 使用稳定 hash 将 token 映射到 256 维向量，再执行 L2 归一化。

class TextEmbedder(Protocol):
    def embed(self, text: str) -> EmbeddedText: ...

class LocalHashingEmbedder:
    model = "local-hashing-v1"
    def embed(self, text: str) -> EmbeddedText:
        # token -> stable dimension -> normalized vector
优点代价
没有模型下载、API key 或网络依赖主要捕捉词面重合，不能可靠理解同义词
测试结果稳定，适合学习相似度与排序哈希冲突会引入噪声
通过协议可替换真实 embeddingSQLite 线性扫描不适合大量文档

这是一种工程上的“先建立可验证基线”策略。面试中应主动说明它的限制，而不是把它包装成生产级语义搜索。

5. Top-K 检索与余弦相似度

本项目把所有向量归一化。归一化后余弦相似度等于向量点积，因此排序代码只需比较对应维度的乘积和：

score = sum(left_value * right_value
            for left_value, right_value in zip(query_vector, chunk_vector))
ranked = sorted(scored, key=lambda item: (-item.score, item.chunk.sequence))[:limit]

用 sequence 作为同分时的第二排序键，保证结果确定。检索 API 返回的不是“神秘上下文”，而是能被用户复核的文本、页码、章节和 score。

6. Grounded Answer：模型只能看到证据

answer_question() 先调用 retrieve_chunks()，再把每块格式化为带来源标签的 evidence。它不会传入整篇 extracted_text。

[chunk:7; page:3; section:2 Method]
The method retrieves evidence before generating an answer.

system prompt 明确要求：仅根据 supplied evidence 回答；证据不足时承认不足；不得编造事实。提示词不能数学保证模型不幻觉，因此 API 还必须将同一批 citations 返回给客户端。

产品上的关键判断

一个流畅但没有来源的回答不是可靠 RAG。引用既帮助用户判断，也让开发者能区分“检索找错了”与“模型没有遵守证据”。

7. API 契约与错误语义

场景响应调用方应做什么
Paper 或 PDF 不存在404先创建论文或上传 PDF
尚未建立索引409调用 retrieval:index
空问题、无词面相关证据422修改问题或提高索引质量
模型配置缺失503设置本机 LLM 环境变量
上游模型失败502提示稍后重试，记录上游故障

limit 限制为 1 到 10。过大的 Top-K 会增加噪声与模型上下文成本；过小则可能遗漏关键论证。第 4 周从默认 3 开始，并将在第 5 周用评测集讨论它。

8. 测试：不是只测“能返回答案”

  • 未索引搜索返回 409，证明索引状态是显式契约。
  • 搜索命中正确页码与章节，验证引用数据没有丢失。
  • Fake AnswerGenerator 断言只接收到 Top-1 证据，防止业务层偷偷传整篇文档。
  • 空和无关 query 返回 422，避免用无意义的结果触发生成。
  • 问答已建立索引但没有配置 LLM 时返回 503，避免意外外部调用。

10. 常见误区

“有向量”不等于“有语义理解”

哈希词向量会受相同 token 驱动。它可以教学与回归测试，但不能用来证明系统在真实论文语义检索上表现良好。

不要先生成、后补引用

正确做法是 citations 与生成时实际提供的 evidence 来自同一个列表。事后另搜一遍再拼引用，可能使引用与模型输入不一致。

不要把 score 当置信度

余弦相似度只描述当前向量空间的相对接近度，不代表答案正确概率。需要人工标注或固定评测集才能判断检索质量。

11. 建议独立练习

  • 实现 OpenAICompatibleEmbeddingClient，遵守同一个 TextEmbedder 协议，并在测试中用 mock 验证模型版本与维度保存。
  • 给 search 增加最小 score 阈值参数，设计默认值并写出“无结果”测试。
  • 建立 10 个“问题 → 正确页码”样本，计算 Recall@1 和 Recall@3。
  • 让 citations 新增原文字符范围，思考页码与 chunk 在长页中的定位差异。
  • 比较一次 token 词面查询与一次同义词查询，记录 hashing baseline 的失败案例。

12. 第 5 周：评测与真实检索基础设施

下一阶段应先建立固定问题集和目标证据页码，量化 Recall@K、MRR、引用正确性与回答覆盖度；然后接入真实 embedding、向量数据库或 ANN 索引，拿同一评测集与当前基线对照。这样引入新技术是基于数据，不是因为“看起来更高级”。
