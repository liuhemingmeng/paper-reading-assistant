第 13 周：GitHub 同类项目对比分析与改善路线图

同学竞品调研架构对标改善优先级

一句话结论：本项目的工程质量与评测闭环已经强于绝大多数轻量开源项目（清晰分层、65 测试、IR 指标 + faithfulness 评估、可续跑缓存），但产品化与检索架构落后一代：当前 API 是「单篇论文维度 + SQLite JSON 暴力余弦」，而成熟的 paper RAG（paper-qa / RAGFlow）是「语料库维度 + 向量库 ANN + 重排/混合检索」，且都有前端与鉴权。把跨库检索 + pgvector（已装好）+ 最小前端 + 鉴权补齐，即可从「评测原型」跃迁为「可上线产品」。

一、调研方法

为找可对标项目，在 GitHub 上调研了两类：

  • 深度 / 生产级标杆：Future-House/paper-qa（学术论文 RAG QA 标杆）、infiniflow/RAGFlow（文档 RAG 引擎，国产）。
  • 轻量 / 同源对标：Guri10/QueryGenie（arXiv ML 论文问答，FastAPI+React+FAISS）、hrushik98/Arxiv-researcher（单篇 arxiv 对话，per-paper Qdrant + 前端 + 鉴权）、gpscal/rag-research-assistant、shashankag14/arxiv_chatbot（Streamlit 轻量版）。

信息来源：各仓库 GitHub README（WebFetch 直读）+ GitHub 搜索结果，聚焦「检索维度 / 向量库 / 重排 / 引用 / 评估 / 前端 / 鉴权 / 部署」等可比维度。

二、代表项目速览

paper-qa（Future-House）

学术论文 RAG QA 标杆 · Python 库 + CLI
  • Agentic 检索：LLM 调度 search→gather evidence→answer 迭代
  • LLM 重排 + 上下文摘要（RCS），evidence 分数 cutoff 控幻觉
  • in-text citations (Author2011 pages 1-2)，自动拉 Crossref/Semantic Scholar 元数据
  • 向量：默认内存 Numpy，大规模用 Qdrant
  • 评估：LitQA2 基准（自称超人类）
  • 无 Web UI

RAGFlow（infiniflow）

文档 RAG 引擎 · 国产 · Docker 镜像
  • DeepDoc 深度解析：版式/表格/公式/OCR、邮件格式
  • 模板化分块（智能可解释）
  • 向量引擎：Elasticsearch / Infinity 可切换
  • 完整 Web UI + grounded citations 减幻觉
  • 部署：官方 Docker 镜像
  • 未内置模型效果评测

QueryGenie（Guri10）

轻量可上线范本 · FastAPI + React + FAISS
  • 跨库检索：arXiv→FAISS（all-MiniLM-L6-v2，24k chunks）
  • 前后端分离：React 18 + TS + Tailwind 前端
  • 把 FAISS 索引提交进 repo 实现零成本部署（Render.com）
  • 无重排、无鉴权、无评测

Arxiv-researcher（hrushik98）

单篇维度对标 · 最像本项目
  • per-paper Qdrant 索引（和我们的 per-paper SQLite 同思路）
  • 混合检索：dense(bge-small) + sparse(bm25) + RRF(0.7/0.3) + cross-encoder rerank
  • Next.js 前端 + 邮箱密码鉴权（Neon Postgres + JWT）
  • PDF 侧栏渲染 + Highlight & Ask
  • 临时存储（容器停即删）

四、本项目已经做对的事（别动）

  • 清晰分层架构：api / services / database / schemas / embeddings / retrieval / llm_client / evaluation 职责分离，易测易改。
  • 评测闭环领先：IR 指标（recall/mrr/ndcg）+ faithfulness judge + 真实 QA 基准 harness，大多数轻量项目完全没有评测。这是你面试/简历的差异化亮点。
  • 工程健壮性：规范错误映射（404/422/409/502/503）、可续跑缓存（cache_io 解决 Windows 文件锁）、65 单测。
  • 引用与忠实度 API 已存在：/questions:answer 返回带 citation 的 grounded 答案，/answers:evaluate 可跑 faithfulness——比 QueryGenie/Arxiv-researcher 更严谨。
  • 已选定并经基准验证的配置：bge-m3 + deepseek-v4-flash + 1000/120 chunking，无需再横测。

五、可改善项（按价值排序）

P0 上线必须具备

1. 跨语料库检索（最关键的架构缺口）

现状：所有检索路由都是 /papers/{paper_id}/search（单篇维度），跨 129 篇语料库的检索完全没有 API 支持——我们的 demo/benchmark 是绕过 API 直接读缓存文件做的。而 paper-qa / QueryGenie / RAGFlow 都是集合/库维度检索，这才是 RAG 的核心价值。

借鉴：paper-qa 的 Docs（一个论文集合）、QueryGenie 的全局 FAISS。怎么做：新增 /library/search 与 /library/questions:answer，支持「在全部已索引论文里检索/问答」，沿用现有 retrieve_chunks 逻辑但去掉 paper_id 过滤。

2. 接入 pgvector（替代 SQLite JSON 暴力余弦）

现状：向量以 vector_json 长文本存 SQLite，检索时把该 paper 所有 chunk 向量 load 进内存逐条算余弦——129 篇×13976 chunk 会慢、吃内存、无法 ANN。pgvector 容器已在华为云 ECS 装好（vector 0.8.6，功能验证通过）但没接进 API。

怎么做：把 ChunkEmbedding.vector_json 迁到 pgvector 的 vector 列，检索用 <-> 运算符 + ivfflat/hnsw 索引；这同时解决规模、并发、持久、故障恢复四个上生产的硬伤（第 12 周教程已列为第一基石）。

3. 最小前端 UI + 鉴权

现状：只有 FastAPI /docs，公网裸奔（无 API Key/JWT）。所有对标项目（除 paper-qa 库）都有前端；Arxiv-researcher 还有 JWT 鉴权。用户没有 UI 就无法用。

借鉴：QueryGenie 的 React 聊天页、Arxiv-researcher 的 Next.js + JWT。怎么做：先用一个静态聊天页（HTML+fetch）打通 /library/questions:answer；鉴权加 FastAPI 依赖（API Key 或 JWT），未带 token 返回 401（第 12 周部署 8 步已规划）。

4. Dockerfile 入仓库 + 生产进程

现状：Dockerfile 在服务器 /opt/rag，未纳入版本控制；__main__.py 用 uvicorn reload 开发模式。怎么做：仓库加 Dockerfile（python:3.11-slim）+ gunicorn -k uvicorn.UvicornWorker -w 2，取消 compose 里 app 服务注释（脚手架已备好）。

P1 体验与质量增强

5. reranker 接入 API + 可选混合检索

代码已有 rerank.py（qwen3-rerank-4b/0.6b）和 BM25Retriever，但 API 检索只用 embedder。借鉴 Arxiv-researcher 的 dense+sparse+RRF+cross-encoder：默认 bge-m3 单阶段（已验证够强），对难问题启用「BM25 + bge-m3 → RRF 融合 → reranker 精排」两阶段。

6. 多轮对话 / 历史

现状：/questions:answer 无状态。借鉴 arxiv_chatbot 的 memory：加会话表存历史，把前轮 Q&A 作为上下文拼进 prompt，支持「追问」。

7. arXiv / 论文元数据自动拉取

借鉴 paper-qa（Crossref/Semantic Scholar）：上传 arxiv 链接后自动补全标题/作者/摘要/引用数，省去手填 metadata，也为 citation 提供规范出处。

P2 差异化（可选）

8. 文档解析增强：借鉴 RAGFlow DeepDoc，加表格/版面对齐的 chunking、扫描件 OCR，提升中文行业 PDF 的召回质量（当前 PyMuPDF 仅抽文本）。
9. 评估接成持续回归：把现有 benchmark harness 接成 CI 或一键脚本，每次改检索逻辑自动跑 IR 指标，防止退化。
10. 自托管 embedding：bge-m3 可本地部署，规避云上外部 API 的网络抖动（我们之前就踩过 SSL 断流）。

六、建议实施顺序（路线图）

1
接 pgvector + 跨库检索 API（P0-1/2 合并，复用已装容器）。这是地基，做完检索质量与规模问题一并解决。
2
Dockerfile 入仓 + gunicorn 生产进程 + Nginx 反代（P0-4），华为云安全组开 80/443。
3
最小前端聊天页 + API Key 鉴权（P0-3），端到端公网可访问。
4
reranker 接入 + 混合检索 + 多轮对话（P1），体验对齐 Arxiv-researcher。
5
arXiv 元数据自动拉取 + 解析增强 + 评估回归（P2），形成完整产品闭环。
投入产出比最高的第一刀：先做 P0-1/2（pgvector + 跨库检索）。它不改变你已做对的架构与评测，只把「单篇暴力余弦」升级为「跨库 ANN 向量库」——一次性补齐规模、并发、持久、跨库检索四个最大短板，且华为云环境已就绪。

七、风险提示

  • 不要为「追平 RAGFlow」过度设计：DeepDoc 级解析投入巨大，且与你的实习目标（RAG/Agent/Python 后端）不匹配；聚焦检索架构 + 产品化即可。
  • 评测资产是你的护城河：保持 IR 指标 + faithfulness 闭环，面试时能讲清「为什么选 bge-m3、怎么验证 recall、怎么防幻觉」远比「又接了个前端」值钱。
  • 密钥安全：华为云 /opt/rag/.env 已预填 API key（gitignored）；本地项目 .venv/KeyPair-a7de.* 仍建议删除，避免打包泄露。
