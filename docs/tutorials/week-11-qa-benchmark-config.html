第 11 周：chunk 切分、真实 QA 基准与生产配置收敛

同学chunk 策略真实 QA 基准配置选型

把「自然语言问题 → 证据段落」的端到端检索链路搭起来并验证可用，然后在 embedding 端点开始随机断流、全量横测性价比过低时，主动收敛到一组直接可上线的配置，不再继续横测。

一、本周做了什么 / 为什么停横测

第 10 周留下了三个待办：① 真实 LLM 答案质量闭环；② 用「自然语言问题→证据段落」真实问答对重跑 reranker 基准（reranker 的主场）；③ 4-LLM 质量/延迟/成本对比。本周把它落地成代码：

  • src/paper_api/chunking.py：滑动窗口 chunk 切分，带 doc_id 溯源。
  • scripts/build_qa_dataset.py：用 LLM 把证据段落改写成自然语言问题，生成 30 条真实 QA（15 arXiv + 15 行业）。
  • scripts/benchmark_qa_retrieval.py：chunk 级真实 QA 检索基准（6 基础检索器 × 2 reranker，doc_id 为正例，可续跑）。
  • src/paper_api/cache_io.py：原子写 + 周期落盘 + 瞬态锁非致命降级的缓存工具（修掉 Windows 下 OneDrive/IDE 文件锁导致的 PermissionError）。
全量横测被主动叫停：全量要把 13976 个 chunk × 多个 embedding 模型逐条走网络；而 embedding 端点现在随机断 SSL 连接（SSL: UNEXPECTED_EOF_WHILE_READING），且第 9-10 周文档级基准已经把 embedding / reranker 结论钉死，横测边际价值极低。因此不再为「补齐所有组合的数字」烧钱烧时间——直接用已有结论选配置（见第六节）。

二、chunk 切分模块

之前第 4/5/9 周都是整篇或按页分块。真实 RAG 需要更细的滑动窗口，让一段证据恰好落在一个 chunk 里，避免「答案被页边界劈开」。

# src/paper_api/chunking.py
chunk_document(text, doc_id, size=1000, overlap=120)
chunk_corpus(docs, size=1000, overlap=120)   # 返回 [ (chunk_id, doc_id, text), ... ]
  • size=1000 / overlap=120：约 1000 字一段，相邻段重叠 120 字，兼顾「语义完整」与「边界不漏」。这是初版默认值，后续可按答案长度做消融。
  • 每个 chunk 记录来源 doc_id，QA 基准用它做正例标注（问题来自哪篇文档，哪篇就是该问题的正例）。
  • 129 篇真实文档切成 13976 个 chunk（本项目的真实检索规模）。

三、真实 QA 数据集（30 条）

build_qa_dataset.py 让 LLM 读证据段落、改写成「人真的会问的问题」，而不是用标题当问题（已知项检索的缺陷：标题天然和自身高度相似，高估检索器）。样例问题：

  • 中文行业：「采购项目预算金额是多少？」「该标准适用于哪些产品？」
  • 英文 arXiv：「what are the main challenges in neural IR?」「how does late interaction retrieve?」
数据集结构：{"items":[{"question":..., "doc_id":..., "source":"arxiv|industry", "evidence":...}]}，30 条（15 arXiv + 15 行业，12 中文 / 18 英文问题）。它证明了「证据段落 → 自然语言问题」的改写链路可用，是 reranker 真正的主场评测集。

五、踩坑：两个崩溃，两种修法

1) Windows 文件锁 PermissionError（已修）

原脚本「末尾一次性 flush」缓存，恰好撞上 OneDrive/IDE 同步瞬间锁文件 → 整轮白跑。cache_io.py 改为：临时文件 + os.replace 原子写、每 300 chunk 周期落盘、瞬态锁降级到 .bakretry 不抛异常。单元验证通过。

2) Embedding 端点 SSL 断流（外部问题，无法在代码内根治）

全量跑到一半，embedding 接口返回 SSL: UNEXPECTED_EOF_WHILE_READING。这是服务端/网络抖动，cache_io 管不了网络层。此时已编码的 chunk 向量靠周期落盘存活在磁盘，但 bge-m3 缓存只到 1463/13976（不完整）。要补完就得再砸 1.25 万次网络 embedding 调用——既慢又正好会再撞 SSL。这正是「停横测」的直接触发点。

结论：当「补齐数字」需要重新发起上万次不稳定的网络调用、且结论早已被更便宜的实验钉死时，继续横测是赔本买卖。配置选型应基于已有证据，而非追求「所有组合都跑满」。

六、最终推荐配置（基于第 9-10 周已验证结论）

不跑全量横测，也能从文档级基准（129 篇真实文档）直接推出生产配置：

角色选择证据
Embedderbge-m3文档级 R@1=0.953（最强），中英文均衡，1024 维
Reranker默认关闭接在 bge-m3 上增益≈0（−0.016）；仅当接弱检索器（BM25/local-hashing）时启用 qwen3-rerank-4b 救回召回
LLMdeepseek-v4-flash-260425首响延迟最低 3.1s，deepseek 中文强，flash 便宜（第 10 周选定）
Chunking1000 / 120初版默认值，后续按答案长度消融
喂 LLM 段数top-10召回够宽，避免漏证据；成本可控

落地到 .env

# 生产部署配置
EMBEDDING_MODEL=BAAI/bge-m3            # 文本检索最强, 中英文均衡
# reranker 默认不接: 在 bge-m3 上增益≈0, 省成本/延迟
#   仅弱检索器(BM25/local-hashing)场景启用 qwen3-rerank-4b
LLM_MODEL=deepseek-v4-flash-260425     # 延迟最低 3.1s, 中文强
# CHUNK_SIZE=1000 / CHUNK_OVERLAP=120 在 chunking.py 默认
# 检索 top-N=10 喂给 LLM
这套配置 = 「强 embedding 单阶段召回 + 快 LLM 生成」。两阶段（加 reranker）只在接入弱检索器时才有正收益，强 embedding 场景下纯属增加延迟与成本。

七、可选：单配置验证（不强制）

如果你想要「选定配置真的端到端跑通」的实锤，可以等 embedding 端点稳定后做一次性验证（不再是横测）：只用 bge-m3 一个检索器（不接 reranker），对 30 条 QA 跑检索 + 用 deepseek-v4-flash 生成答案。届时 bge-m3 缓存需从 1463 补到 13976——但那只是「验证」，不是「对比」，规模可控。

当前 bge-m3 缓存 1463/13976、qwen3-embed-0.6b 13763/13976（接近完整）。离线 Fake 链路 + 单测仍保证每次提交可回归检索命中与引用正确性，不依赖任何外部凭据。

八、局限与下一步

本阶段局限：真实 QA 检索基准只跑了 smoke（pipeline 验证），未出全量数字；4-LLM 答案质量/延迟/成本横评未跑。这两项的结论已被第 9-10 周更便宜的实验覆盖，因此主动停掉，不做赔本的横测。

下一步（按价值排序）：

  1. 端到端 RAG demo：用上面的推荐配置跑一个真实问答（检索 bge-m3 → deepseek-v4-flash 生成 → 返回带 citation 的答案），作为简历可展示的成品。
  2. 答案质量闭环：接入真实 LLM 后用 scripts/evaluate_answers.py --faithfulness（qwen3.5-35B 作独立裁判）验证忠实度。
  3. 消融（可选）：chunk 大小、喂 LLM 段数、是否接 reranker 的少量对照，而非全组合横测。
