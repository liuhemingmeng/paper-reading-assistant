Week 9RAG 评测真实语料

多模型检索基准：129 篇真实文档上的检索器与重排器对比

为什么做、怎么做、结果说明白 —— 以及对「实验太简单」质疑的正面回应

1. 背景：为什么需要这个基准

第 8 周的对比实验用了 6 页合成文档 + 12 句问句，你当时提出了一个尖锐但正确的质疑：文档是不是真的？数量够吗？只对比两种检索器，未来换模型怎么办？

这一周我们正面回应这三点：

  • 真实文档：用 5 个子代理搜集了 138 篇公开文档，其中 129 篇成功下载并抽取出可检索文本（95 PDF + 24 HTML + 8 TXT + 2 MD）。
  • 数量与多样性：覆盖 arXiv 三领域（检索/RAG、LLM/Agent、Embedding）共 79 篇英文论文，以及 50 篇中文行业资料（金融/招采/技术白皮书/法规/标准）。
  • 多模型可扩展：把对比从「2 个检索器」扩成 6 个基础检索器（本地哈希 / BM25 / 4 个语义 embedding）+ 3 个 reranker，新增模型只改注册表、不碰评测代码。
核心结论先讲：在「用自己的标题找自己」这种已知项检索任务上，BM25 已经很强（R@1=0.915），语义 embedding 分高下，而 reranker 的真正价值在于救回弱召回——接在 local-hashing 或 VL-embedding 后面能把 R@1 从 0.33 / 0.43 拉到 0.86+。

3. 评测方法

3.1 任务定义：已知项检索（Known-Item Retrieval）

对每篇文档 D，以其标题作为查询 q，正样本就是文档 D 自身。判断：用 q 去检索全部 129 篇，D 有没有排进 Top-K。

为什么用标题当查询？ 因为 manifest 里只有 title、没有 abstract。这反而更公平：标题词与正文天然重叠，对词法检索（BM25/哈希）是送分题，对语义检索才是真考验——能直观暴露「词汇重叠」vs「语义理解」的差距。代价是任务比真实 RAG 的「自然语言问题→证据段落」更简单，结论要克制（见第 6 节）。

3.2 六个基础检索器

  • local-hashing：SHA-256 hashing trick，256 维，无模型无网络，只捕捉词汇重叠（最弱基线）。
  • bm25：Okapi BM25，词法检索金标准，复用项目统一的 TOKEN_PATTERN。
  • volcano-vision-251215：火山多模态 embedding（2048 维）。
  • siliconflow-qwen3vl-embed-8b：Qwen3-VL 视觉语言 embedding（4096 维）。
  • siliconflow-qwen3-embed-0.6b：Qwen3 文本 embedding（1024 维）。
  • siliconflow-bge-m3：BAAI bge-m3（1024 维）。

注：火山 doubao-embedding-large-text-250515 在接入冒烟时返回 404（模型处于 Retiring/未开通状态），按你的决定跳过，不计入基准。

3.3 三个 reranker（接在每个基础检索器后面）

每个 reranker 作用在「对应基础检索器的 Top-30 候选」上做交叉编码重排，报告「X 检索器 + reranker_Y」组合指标，以及与 X 单独使用的增益 Δ。

  • qwen3vl-rerank-8b / qwen3-rerank-4b / qwen3-rerank-0.6b（硅基流动，端点 /v1/rerank）。

3.4 指标

对每个查询计算二元相关性（命中/未命中），语料级聚合：

  • Recall@K：正样本是否在前 K 个结果里（K=1/3/5/10）。
  • MRR@10：第一个命中结果排名的倒数的均值，最敏感于 Top-1 质量。
  • nDCG@10：带位置折扣的排序质量（已知项任务里正样本唯一，退化为命中位置的折扣）。

实现见 src/paper_api/ir_metrics.py（纯 Python，无 numpy 依赖）。embedding 向量按模型缓存到 data/embed_cache/，reranker 结果按「reranker+基础器」组合缓存到 data/rerank_cache/ 并周期落盘——可续跑，被超时杀掉后只补未完成组合。完整脚本：scripts/benchmark_retrieval.py。

5. 五个关键发现

  1. 文本 embedding 里 bge-m3 与 qwen3-embed-0.6b 最强。 整体 R@1 分别 0.953 / 0.922，且在 arXiv 英文上 bge-m3 高达 0.987。它们明显优于词法基线 BM25（0.915）和火山多模态 vision 模型（0.868）。
  2. 视觉语言 embedding（qwen3vl-embed-8b）不适合纯文本检索。 整体 R@1 仅 0.426，在 arXiv 英文论文上更是暴跌到 0.241——VL 模型为图文对齐训练，文本标题检索不是它的主场。但它在中文行业资料上回升到 0.720，说明对中文/混合内容仍有局部价值。结论：别用 VL embedding 当通用文本检索器。
  3. reranker 的真正价值是救回弱召回，不是锦上添花。 接在 local-hashing（0.333→0.86，Δ+0.53）和 qwen3vl-embed（0.426→0.89，Δ+0.47）后面增益巨大；接在已经很强的 bge-m3/bm25 后面几乎无增益，甚至 qwen3-rerank-4b + bge-m3 出现 −0.016 的轻微负增益。
  4. 中文行业资料比英文论文更难检索。 所有检索器在 industry 上的 R@1 普遍低于 arxiv（例如 bge-m3：0.987→0.900，local-hashing：0.354→0.300）。原因：中文标题与正文的词汇重叠更稀疏、文档类型更杂（招采/法规/年报混排）。
  5. 已知项检索对词法是送分题。 BM25 R@1=0.915 说明「标题找自己」时词面重叠足够强，这也是 reranker 在强检索器上增益有限的根因——任务本身不够难。

6. 局限与下一步

这个基准的边界（写进简历前必须清楚）：
  • 已知项检索 ≠ 真实 RAG。 真实场景是「自然语言问题 → 证据段落」，reranker 的增益会在那种任务上被显著放大。本基准低估了 reranker 价值。
  • 单正样本 + 二元相关性。 每篇文档只有一个正样本（自身），没考虑「多个文档都相关」的多义查询；nDCG 因此退化为位置折扣。
  • 标题查询词汇泄漏。 标题词天然出现在正文，对词法检索偏利。
  • 中文子集只有 50 篇。 分组指标的方向性可信，但绝对值的置信区间较大。

下一步（生产级闭环）

  • 构造真实问答对（标题/摘要 → 人工或 LLM 生成的问题），用「问题→证据段落」重跑，才是 reranker 的主场。
  • 接入真实 LLM_*，用 scripts/evaluate_answers.py --faithfulness 跑答案忠实度/质量闭环。
  • 把 embedding 维度、reranker 候选数、chunk 大小作为超参做消融。

7. 怎么复现

# 1) 抽取语料文本（首次，之后走缓存）
python -m scripts.benchmark_retrieval --help

# 2) 跑完整基准（embedding 向量缓存在 data/embed_cache/，
#    reranker 结果缓存在 data/rerank_cache/，可断点续跑）
unset http_proxy https_proxy   # 绕过沙箱代理，直连外部 API
python scripts/benchmark_retrieval.py --out data/benchmark_results.json

# 3) 只看基础检索器（跳过联网 reranker，离线可跑）
python scripts/benchmark_retrieval.py --no-rerank --out data/bench_base.json

密钥只从 .env 读取（火山 EMBEDDING_* + 硅基 SILICONFLOW_API_KEY），不进代码；缺失密钥的模型自动跳过。结果 JSON 结构：overall / by_source / rerankers[*].combos。
