第 14 周：从面试视角看项目改造计划

目标读者：准备 AI 应用 / RAG / Agent 实习面试的同学。本文把《第 13 周 GitHub 对比》的结论翻译成一份可执行的项目修改计划——哪些功能面试必问、必须加；哪些只是「研发过程噪音」、要收敛；哪些是你已经领先、必须保留的差异化卖点。

一句话总纲：面试官不关心你「接了多少模型」，关心你「能不能用数据证明检索质量、能不能端到端跑起来给人看、架构干不干净、工程素养够不够」。本计划就是围绕这四点，做减法聚焦 + 一处关键加法。

一、面试考官怎么看一个 RAG 项目（5 维打分卡）

① 检索质量可量化
有没有 recall / nDCG / faithfulness 等硬指标证明「检索得对、答得准」。
本项目领先 已有 IR 三指标 + faithfulness 评测 harness。
② 能演示、能跑通
能不能打开一个界面真问一句、看到带引用的答案。
本项目缺 只有 API、无前端、且无跨库检索。
③ 工程化可部署
测试、Docker、可上云。
本项目半有 65 单测齐全；缺 Dockerfile 入仓 / CI。
④ 架构清晰
分层、可维护、可读。
本项目领先 api/services/models/schemas/retrieval/embeddings/rerank 分层干净。
⑤ 业务判断力
知道何时用 reranker、怎么切 chunk、为什么 citation 重要。
本项目有 选型决策已写进教程，但代码要落地。

二、必须增加的功能（MUST —— 面试必问，按 ROI 排序）

#功能精确改动点为什么面试加分
1跨语料库检索 services.retrieve_chunks 去掉 where PaperChunk.document_id == document.id 硬过滤；新增 retrieve_corpus(session, query, limit, filters)；api.py 加 POST /corpus/search 或 GET /search?scope=all。
对齐 paper-qa / RAGFlow 的「库级检索」。		 当前 API 只能「在一篇 paper 内搜」，而 RAG 的真正价值是「在全部论文里找答案」。这是与成熟项目最本质的代差，也是考官第一个会问的。
2pgvector 持久化 + ANN 新增 src/paper_api/vector_store.py（pgvector 客户端）；build_retrieval_index 写 pgvector，retrieve_chunks 走 <-> ANN（hnsw）；接华为云已装容器 rag-pgvector。废弃 SQLite vector_json 暴力余弦。 规模 / 并发 / 持久 / 重启不丢，四合一。证明你懂「向量库不是玩具」。
3最小前端 chat UI 新增 frontend/（React+Vite 或纯 HTML+fetch）：输入框 + 答案卡片 + citation 来源列表（点开跳转到 chunk / page）。 面试演示杀手锏——能让考官当场看到「带引用的答案」。多数轻量开源项目都没有。
4API Key 鉴权 新增 src/paper_api/auth.py：APIKeyHeader 依赖 + verify_api_key，路由加 Depends(...)；.env 加 RAG_API_KEY。 「对外开放前的硬门槛」。证明你有安全意识，不是写完 demo 就裸奔公网。
5Dockerfile + compose app 服务 仓库根加 Dockerfile（python:3.11-slim）；华为云 /opt/rag/docker-compose.yml 取消 appbuild: .。 「我能一键部署」的实证。华为云环境已就绪，只差这步。
6多轮对话 / 会话 新增 chat_sessions 表 + POST /chat 路由，把历史注入 prompt。 RAG 体验从「一问一答」升级成「对话」，demo 更像真产品。
7CI（GitHub Actions） 新增 .github/workflows/ci.yml：push 时跑 pytest + ruff。 工程素养的「合格证」。考官看仓库第一眼就会点 Actions。

三、应该删减 / 收敛的功能（DEL —— 避免显得堆砌、不聚焦）

#收敛项具体动作理由
1视觉 / 多模态 embedder volcano-vision-251215、qwen3vl-embed-8b 从选型 / 演示中移除，仅在 registry 保留作可选。 纯文本论文 RAG 用不到视觉编码；留着只会让考官觉得「为了多接而多接」。
2LocalHashingEmbedder 当默认 services.py 里 embedder or LocalHashingEmbedder() 改为默认注入真实 embedder（bge-m3）；hashing 仅作 test fixture。 toy baseline 竟是生产默认，是隐患也是笑话。保留它做单测基准即可，别当 feature。
36 模型横测全组合 scripts/benchmark_*.py 明确归类为「实验 / 评测工具」，README 不把它当核心功能罗列；对外讲「基于指标选型」而非「我接了 N 个模型」。 横测是研发过程，不是产品。堆数字反而稀释重点。
4registry 里 404 的 glm-4-7 标注 unavailable 或移除，避免「可达 LLM 列表」误导。 不可达模型出现在列表里显得粗心。
5reranker 硬接 默认关闭 reranker，仅作为「弱检索器才开」的开关保留。 文档级基准已证 bge-m3 单阶段增益≈0；为「显得高级」硬接 reranker 反而露怯。

四、必须保留的差异化卖点（KEEP —— 别动）

清晰分层架构：api / services / models / schemas / retrieval / embeddings / rerank / ir_metrics 职责分明。这是多数学生项目没有的。
65 个单测 + 离线 Fake 链路：每次提交都能回归检索命中与引用正确性，不依赖外部凭据。
IR 评测闭环：recall / mrr / ndcg 纯 Python 实现 + 已知项 / 真实 QA 两套基准 harness。
faithfulness 评测：独立裁判模型验证答案是否忠于证据——这是 RAG 质量的核心，paper-qa 之外少有轻量项目做。
可续跑 embedding 缓存 + 原子写容错（cache_io.py）：工程细节，面试能讲出「Windows 文件锁 / 网络抖动如何不丢进度」。

六、面试叙事建议（怎么说比做什么更重要）

❌ 不要这样讲

  • 「我接了 6 个 embedding 模型 + 2 个 reranker 做横测」→ 显得堆砌、无重点。
  • 「我用 bge-m3 因为大家都说它好」→ 无数据支撑。

✅ 应该这样讲

  • 「我用 recall / mrr / ndcg 在 129 篇真实论文上量化评测，bge-m3 单阶段 dense 检索 R@1=0.95，接 reranker 增益≈0，所以默认单阶段、弱检索器才开 reranker。」
  • 「答案质量用独立裁判模型做 faithfulness 评测，确保不编造——这是 RAG 落地最容易翻车的地方。」
  • 「向量存在 pgvector，跨 129 篇语料做 ANN 检索，重启不丢；检索和生成解耦，单测覆盖检索命中与引用正确性。」
  • 「部署用 Docker + gunicorn，CI 自动跑测试，前端带 citation 可演示。」
核心卖点一句话：「我做了一个检索质量可量化、跨库检索、带引用且可部署的论文 RAG 助手，并且用指标而非感觉做每一个技术选型。」——这正好是 RAG 岗面试官最想听到的。

七、风险与取舍

  • pgvector vs 保留 SQLite 缓存：建议 pgvector 为主索引，SQLite 缓存仅作离线测试 fixture，避免双写不一致。
  • 跨库检索的权限边界：Phase 1 先全库公开检索，Phase 2 鉴权后再考虑「按用户 / 按文集过滤」。
  • 前端技术选型：若赶时间，纯 HTML + fetch 即可（1 天），不必上 React；面试看的是「能演示 + citation」，不是框架。
  • 不要本末倒置：Phase 1（跨库 + pgvector）是 ROI 最高、最该先做的；前端 / CI 是「锦上添花」，但面试演示缺一不可。
