2. 项目结构与职责

paper-reading-assistant/
├── pyproject.toml          # 项目元数据、测试和打包配置
├── requirements.txt        # 最小开发依赖：pytest
├── .env.example            # 环境变量名称模板，不存秘密
├── .gitignore              # 不提交虚拟环境、密钥、缓存、生成数据
├── scripts/                # 可独立运行的学习脚本
├── src/todo_cli/           # 可导入的 Todo CLI 包
├── tests/                  # 自动化测试
├── data/                   # 本地运行产生的数据，JSON 默认不提交
└── docs/tutorials/         # 每次任务完成后的教程文档

为什么脚本放在 scripts/，应用放在 src/？

scripts/ 中是单文件练习，它们可以直接通过 python scripts/xxx.py 运行；src/todo_cli/ 是多模块应用，内部模块通过相对导入协作，例如 from .storage import load_todos。把应用代码放入 src/ 是常见工程布局，它能防止你在项目根目录偶然导入了还没正确安装的代码。

容易踩的坑

仅仅存在 src/todo_cli 并不意味着 python -m todo_cli 能运行。必须执行 python -m pip install -e .，或明确配置 Python 路径。这里选择可编辑安装，因为源码修改后立即生效，更接近真实开发工作流。

3. Python 环境与依赖

3.1 虚拟环境解决什么问题？

虚拟环境 .venv 是这个项目自己的 Python 解释器和第三方库目录。没有它，所有项目会共享系统 Python 的包版本；当 A 项目要求旧版库、B 项目要求新版库时，环境很快失控。

# 创建虚拟环境
python -m venv .venv

# 安装测试依赖
python -m pip install -r requirements.txt

# 将 src/ 下的项目以“可编辑模式”安装
python -m pip install -e .

python -m pip 的含义是“使用当前这个 Python 解释器运行 pip”。它比裸写 pip 更稳，因为你明确知道依赖装进了哪个环境。

3.2 pyproject.toml 是什么？

它是现代 Python 项目的统一配置文件。本项目中它描述了项目名称、Python 最低版本、开发依赖、pytest 搜索路径，以及如何从 src 找到包。后续加入 FastAPI、SQLAlchemy、Pydantic 时，也应该优先在这里维护依赖声明。

配置意义为什么对后端项目重要
requires-python = ">=3.11"声明代码支持的最低版本部署环境和团队成员不会猜测兼容范围
dev = ["pytest..."]测试属于开发依赖生产环境不需要为了运行服务而安装测试工具
pythonpath = ["src"]测试期间能导入源码包测试与正式安装的导入路径保持一致

3.3 为什么不能提交 .env？

未来调用 LLM 时，API Key 相当于密码。真实密钥只应保留在本机环境变量、部署平台的 Secret 配置或本地 .env 中。仓库只提交 .env.example，它记录“需要哪些变量”，而不是“变量的真实值”。

4. 五个基础脚本：每一个都在训练工程能力

4.1 文件批处理：pathlib 与 dry-run

file_batch.py 用 Path 表达路径，并用 directory.iterdir() 找到当前目录下的文件。核心函数 rename_files() 先计算所有重命名计划，只有传入 --apply 才真正改名。

files = sorted(path for path in directory.iterdir() if path.is_file())
plans = [
    (path, directory / f"{prefix}_{index:03d}{path.suffix}")
    for index, path in enumerate(files, start=1)
]
  • sorted(...)：保证每次生成的编号稳定，避免目录读取顺序导致结果漂移。
  • enumerate(..., start=1)：同时得到编号和文件对象。
  • {index:03d}：把 1 格式化为 001，文件名排序更自然。
  • path.suffix：保留原始扩展名，不把 .pdf 误改成无后缀文件。
  • dry-run：这是涉及文件修改时应形成的默认习惯。先展示计划，再执行。
# 只预览
python scripts/file_batch.py data --prefix demo

# 确认计划后才执行
python scripts/file_batch.py data --prefix demo --apply

4.2 JSON / CSV：结构化数据不是字符串拼接

data_io.py 训练两个最常见的数据格式。JSON 适合保存嵌套对象，CSV 适合表格数据。未来论文记录的最初版本可以用 JSON，进入 FastAPI + SQLite 后再迁移到数据库。

选择原则：配置、嵌套请求/响应、临时结构化结果用 JSON；二维表格导入导出用 CSV；多用户、查询、并发和关联关系进入 SQLite/PostgreSQL。

4.3 API 调用：网络不是可靠的

api_client.py 使用标准库 urllib 发送 GET 请求，并区分 HTTP 错误、网络错误、超时和无效 JSON。它的价值不在于调用一个特定 API，而在于建立调用外部服务时的底线：配置来自环境、请求必须有 timeout、错误要转换为可读信息、响应需要落盘才可复查。

try:
    with urlopen(request, timeout=timeout) as response:
        return json.load(response)
except HTTPError as error:
    raise RuntimeError(f"API returned HTTP {error.code}") from error
except URLError as error:
    raise RuntimeError(f"API request failed: {error.reason}") from error

raise ... from error 会保留原始异常链。对用户展示的是简洁错误，对日志和调试保留根因。后续接入 LLM API 时，这个习惯非常重要。

4.4 重试：只重试可能恢复的错误

retry_demo.py 实现指数退避：第 1 次失败等 0.5 秒，第 2 次等 1 秒，第 3 次等 2 秒。公式是 base_delay * 2 ** (attempt - 1)。

for attempt in range(1, attempts + 1):
    try:
        return operation()
    except Exception:
        if attempt == attempts:
            raise
        delay = base_delay * (2 ** (attempt - 1))
        sleep(delay)
工程判断

演示代码为了聚焦写法捕获了 Exception。真实 LLM / HTTP 调用中，应只重试可恢复错误，例如超时、连接中断、429 限流、部分 5xx；不要对 400 参数错误、401 鉴权失败、JSON 格式错误做盲目重试，否则只会浪费调用次数和费用。

函数把 sleep 作为参数注入，默认是 time.sleep。测试时可以传一个空函数，从而不必真的等待。这是“依赖注入”的小型实例。

4.5 命令行参数：把程序变成工具

argparse 负责把用户输入的字符串变成结构化的 args 对象，并免费提供 --help、类型转换和缺失参数报错。以后 FastAPI 的请求模型也在做相似的事情：把外部输入变成可信的程序数据。

parser.add_argument("topic", help="Topic to print.")
parser.add_argument("--pages", type=int, default=1)
parser.add_argument("--tag", action="append", default=[])
  • 没有 -- 的 topic 是位置参数，必须按顺序提供。
  • --pages 是可选参数，type=int 会提前把字符串转换为整数。
  • action="append" 允许重复传入 --tag python --tag rag。

5. Todo CLI：从单脚本到小型应用

Todo CLI 的业务很简单，但分层方式与后续论文管理 API 一致：数据模型、存储层、命令接口层分开。这样 FastAPI 出现后，你主要替换“命令接口层”，不需要推翻业务和存储逻辑。

模块职责不该做什么
models.py定义 Todo 数据及自身校验不读写文件，不解析命令
storage.py读写 JSON，转换存储错误不判断用户执行的是 add 还是 delete
cli.py解析参数、编排业务、打印结果不把 JSON 细节散落到每个命令里
__main__.py使 python -m todo_cli 可执行不放业务逻辑

5.1 数据模型：dataclass 与不变量

Todo 有 id、title、completed 和 created_at。__post_init__ 在对象创建后立即去除标题两侧空格，并拒绝空标题。

@dataclass
class Todo:
    id: int
    title: str
    completed: bool = False

    def __post_init__(self) -> None:
        self.title = self.title.strip()
        if not self.title:
            raise ValueError("Todo title cannot be empty")

这叫维护不变量：只要一个 Todo 成功创建，就可以相信它的标题非空。不要把这个校验只写在 CLI 层，因为未来 API、脚本、批处理都可能创建 Todo。

5.2 存储层：文件不存在不是错误，文件损坏才是

def load_todos(path: Path) -> list[Todo]:
    if not path.exists():
        return []
    raw_data = json.loads(path.read_text(encoding="utf-8"))
    return [Todo.from_dict(item) for item in raw_data]

第一次使用时没有数据文件是正常状态，所以返回空列表。反过来，文件存在但不是合法 JSON，则说明数据损坏或被手工改坏，应该抛出 TodoStorageError，不能静默当成空列表，否则用户会误以为数据丢失。

ensure_ascii=False 让保存的中文保持可读；indent=2 让 JSON 适合人工检查。

5.3 CLI 层：命令、业务、输出的边界

python -m todo_cli add "Read a RAG paper"
python -m todo_cli list
python -m todo_cli done 1
python -m todo_cli delete 1

build_parser() 只定义输入契约；run_command(args) 根据命令调用业务逻辑并返回字符串；main() 只负责解析、打印和把预期错误转换为退出码 1。这个拆分带来的直接好处是：测试可以直接调用 run_command()，无需真的启动子进程和捕获终端输出。

6. 异常、日志与配置：这是工程质量的分水岭

6.1 三种输出不要混在一起

类型面向谁示例
正常输出 print命令使用者Added todo 1: ...
日志 logging开发者 / 运维者重试次数、文件路径、堆栈信息
异常 raise调用者或上层边界标题为空、JSON 损坏、网络调用失败

在 storage.py 中，低层 JSONDecodeError 会转换为领域错误 TodoStorageError。这样 CLI 不需要理解 JSON 库的细节，只需要知道“存储不可用”。这就是异常抽象边界。

6.2 错误处理不是吞错

正确模式：捕获你能解释或恢复的错误，记录上下文，转换成上层能处理的异常；到 CLI/API 最外层再形成用户可读响应。

错误模式：except Exception: pass。这会掩盖真实 bug，也会在后续 RAG 项目里造成“回答为空但不知道为什么”的灾难。

7. 测试如何证明功能

测试不是为了凑数量，而是把关键行为写成可重复的断言。当前 7 个测试覆盖了 Todo 存储与命令行为。

def test_todo_lifecycle(tmp_path: Path) -> None:
    data_file = tmp_path / "todos.json"
    assert run_command(args(data_file, "add", title="Read RAG paper")) == ...
    assert run_command(args(data_file, "done", id=1)) == ...
    assert run_command(args(data_file, "delete", id=1)) == ...

tmp_path 是 pytest 提供的临时目录。测试使用它而不是 data/todos.json，因此不会污染真实数据，也不会因上次运行遗留文件而变得不稳定。

测试类型当前例子未来 RAG 对应物
正常路径添加、完成、删除 Todo上传 PDF 后能生成文档记录
边界条件空标题、空列表空 PDF、超长问题、没有相关片段
异常路径损坏 JSON、未知 IDPDF 解析失败、LLM 超时、向量库不可用
 
python -m pytest -q
python -m compileall -q scripts src tests

第一个命令验证行为是否符合预期；第二个命令验证所有 Python 文件至少能被解析和编译。二者互补，但编译通过不等于业务正确。

8. Git 提交与仓库卫生

当前仓库按工程演进拆成了初始化、脚本、CLI、测试、文档和忽略规则等多个提交。面试时你可以解释每一步在降低什么风险，而不是只展示一个无法阅读的大提交。

chore: initialize Python project structure
feat: add Python fundamentals scripts
feat: add JSON-backed todo CLI
test: cover todo storage and commands
docs: add setup and usage guide
chore: ignore project metadata
  • feat：增加面向用户或项目的功能。
  • test：新增或调整测试。
  • docs：只变更文档。
  • chore：构建、忽略规则、工具配置等杂务。
必须遵守

不要提交 .env、API Key、虚拟环境 .venv、pytest 缓存、真实用户论文或生成 JSON。尤其 LLM 项目常因误传 API Key 导致额度被盗用；发现已经提交密钥时，撤销/轮换密钥比删除文件更重要，因为 Git 历史仍可能保留旧值。

9. 你现在应该独立完成的练习

你提到过去两年有较多代码依赖 AI。解决方法不是强行拒绝 AI，而是把 AI 产出的代码变成你能修改、解释和验证的代码。下面练习按难度递增，每次只做一个，并自己先写 20 分钟。

  • 给 todo-cli list 增加 --completed 选项，只显示已完成任务。先改 build_parser()，再改 run_command()，最后补测试。
  • 给 Todo 增加 priority 字段，限制为 1 到 3。思考校验应该放在模型、CLI 还是两者。
  • 为 file_batch.py 增加 --suffix .txt，只处理指定后缀。注意用户输入可能不带点。
  • 为 with_retry() 写测试：第一次和第二次失败、第三次成功；断言传入的假 sleep 收到 [0.5, 1.0]。
  • 把 api_client.py 的请求方法改为可选的 GET/POST，并思考 POST 请求体应该如何 JSON 编码。
学习循环

先写下你的设计：输入是什么、输出是什么、错误是什么、如何测。然后写最小实现，运行测试，最后才对照教程或询问 AI。每次完成一个练习，提交一个聚焦的 Git commit，并能在不看代码的情况下讲清楚为什么这样改。

10. 如何衔接第 2 周：FastAPI + SQLite

第 2 周不是从零开始，而是把当前的分层能力换到论文管理场景：

当前第 2 周保持不变的原则
Todo 数据类Paper 请求/响应模型模型负责数据结构与校验
JSON 文件存储SQLite 数据库存储细节不散落在接口层
argparse CLIFastAPI 路由外部输入先验证，再调用业务逻辑
run_command() 测试API 客户端测试测试覆盖正常、边界和异常路径

当你能解释上面这张映射表时，FastAPI 就不再是“调库”，而是一个将 HTTP 请求接到已有业务逻辑上的接口层。
